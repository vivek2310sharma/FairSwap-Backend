## Security model
* `wearable_session_bindings_v1` (no client grants) is the authority that ties an upload session to the wearables category. The session core `app_security.impl_posting_session_core_v1` takes the category selector as a parameter, has **no grants to any client role**, and is called only by two definer functions that hard-code their own selector (NULL for phone/accessory; the release-table category for wearables). No transaction setting or marker is used for authorization.
* `zz_wearable_listing_guard_v1` (listings trigger) requires a bound, owned session for a wearables listing, blocks a wearable session from becoming another category, runs the India payment/contact content guard, and **blocks activation of any flagged listing unless the caller is an active moderator** (`listing_wearable_risk_flags_v1`: `other_model`, `other_brand`, `still_paired`, `unknown_pairing`).
* `locked` devices and ownership/stolen declarations are rejected in `validate_wearable_v1`; `still_paired` and `unknown` stay distinct and are never `transfer_ready`.
* Quarantined/excluded catalogue rows cannot be reached through "Other model/brand" (matched on `name_key`/`base_key`).

**Resequenced again.** Tablets V2 `20261104215253` is installed in both hosted ledgers, so the unapplied activation was renamed from `20261104120100` to `20261104220000` (after Tablets V2, before pending moderation switching `20261104223000`). **Production foundation out of order.** Production already holds Tablets V2 `20261104215253`, newer than the foundation. `scripts/release/wearables-v1-release.mjs` (`WEARABLES_OUT_OF_ORDER`) allows exactly that one newer row (exact name and statement digest) for the Production foundation only; the reusable release then runs `supabase db push --include-all` for the dry run and the apply, after the pinned CLI advertises the flag, and the dry run must list only the foundation. Gates enforced before any `supabase db push` (all fail closed, every database query is read-only):

* **Live definitions**: `impl_posting_v2_session` must still be the Accessories baseline, the phone functions, ACLs, session-recovery column and Mobile Phones definition must exist, and no Wearables object may exist (foundation). Activation requires a disabled foundation.
* **Web**: the staging deployment must be READY for `e37e28df1d387a02bcbea19487dfe0f82d198f74` (`WEARABLES_WEB`). Wearables has its own pin; Accessories and Tablets pins are unchanged.
* **Postflight (smoke and integrity, not E2E)**: forced RLS, table and function ACLs, session-core isolation, session/listing ownership invariants, moderation guard trigger and moderator-only flags, catalogue revision, and read-only catalogue/search RPC calls. The receipt records `postflightScope: sql-integrity-smoke-not-e2e`.

* It reads (never writes) the hosted ledger and requires both rows with exact names and pinned JSON-statements digests (`to_jsonb(statements)::text`, sha256): foundation `accessories_v1`, 58 statements, `70f752d5484a4e5a85680e4b2fd8ef5c257fef2f74979bd803fa4db1bf43f772`; activation `activate_accessories_v1`, **1** stored statement, `389d6ee5fcfb047057c9243570661cf4b5096030a2ebb1cbcabb2e26ad11b3bd`. * Its receipt (`ADOPTED_EXISTING_INSTALLATION_VERIFIED`) records `installedByThisWorkflow: false`, `originalReleaseRun: null`, `priorRuns: []`, no Web evidence, and per entry the observed ledger digest, `storedSqlSha256` (read from the hosted ledger at run time), the reviewed source SHA-256 and `matchesReviewedSource` (computed from that comparison, never a constant). Wearables Production accepts that receipt, in place of a release receipt, only if the adoption block equals the registry attestation exactly and the adopting run is a successful `main` dispatch on an ancestor of the release commit. The normal same-commit evidence path is unchanged and still rejects an adoption receipt. The live ledger digests of both rows are re-checked at Wearables release time.

The activation row is a **single stored statement** (not the 7 a CLI split of the file yields), so its JSON-array digest `389d6ee5…` is not derivable from a CLI split. Provenance is instead attested by the exact stored SQL text: read-only comparison of both hosted databases found one statement of 533 characters whose UTF-8 SHA-256 is `3fe0647b33ad914efca86b5a9aa91590be1d2d42ac20eb42cdc5d38ee3baabcd`, byte-identical to the reviewed activation source. At adoption time the database computes `sha256(statements[1])` and the workflow requires it to equal both the pin and the SHA-256 of the reviewed source file read from the commit (`STORED_SQL_HASH_MISMATCH` / `STORED_SQL_SOURCE_MISMATCH`), in addition to the JSON-array digest, the statement count (1) and both ledger rows' names/digests. `matchesReviewedSource` is derived from that run-time comparison. `installedByThisWorkflow: false` and `originalReleaseRun: null` are unchanged.

## W-AZ-1: flagged wearables and the Azure finalizer (fixed in the activation migration)
The installed Azure finalizer (`20261104113705`, history untouched) could choose `auto_approved` for a wearable with risk flags; the Wearables guard (correctly) blocked the update, so finalization rolled back instead of routing to staff. The activation migration now, **before** the category is enabled and in the same transaction:
* requires the installed `app_security.impl_finalize_moderation_result(...)` to be exactly the reviewed Azure body (SHA-256 of `pg_proc.prosrc` pinned to `fb49b713…30be`, definer, empty `search_path`) and not yet wrapped; otherwise it aborts (`WEARABLES_AZURE_BASELINE_DRIFT` / `…ALREADY_WRAPPED` / `…PREREQUISITE_MISSING`). If no finalizer exists at all (only possible in local fixtures; hosted preflight requires Azure) the step is a no-op.
* renames the Azure function to `impl_finalize_moderation_result_azure_v1` (all privileges revoked, including `service_role`) and installs a thin SECURITY DEFINER wrapper under the original name and signature (same ACL: `service_role` only). For `p_outcome = 'no_review_flags'` the wrapper locks the listing row (Azure's own lock order), and if `listing_wearable_risk_flags_v1` has any row for the listing it passes `needs_review`. The Azure body then records the result, completes the request, consumes the receipt and routes to `routed_to_admin` atomically; the listing stays `pending_review`. Authority is the flag rows only: never client declarations, Azure's `no_review_flags`, request claims or any setting. Clean wearables, phones and accessories take the unchanged path.
* The wearables guard, moderator-only AAL2 approval, RLS and ACLs are untouched. Release order is strict: Azure `20261104113705` → Wearables foundation → Wearables activation (`requiredLedgerVersions`). Activation preflight (`azure_finalizer_baseline`) and postflight (`azure_finalizer_wearable_routing`) verify the same facts against the live database.
* Rollback (review-only): `rollback/disable_wearables_v1.sql`, then `rollback/restore_azure_finalizer.sql` (restores the original name; W-AZ-1 then fails closed again — the guard still blocks publication).
* Verify the pin read-only on each hosted database before dispatch: `select encode(sha256(convert_to(prosrc,'UTF8')),'hex') from pg_proc where oid='app_security.impl_finalize_moderation_result(uuid,uuid,text,text,text,text[],text[],jsonb,jsonb)'::regprocedure;` must return the pin above.

## Coexistence with Azure moderation `20261104113705` (native PG17)
`bash tests/wearables-v1/run-native.sh /abs/path/to/pg17/bin --web=/abs/path/to/FairSwap-Web` runs `native.mjs` (16 checks) and `azure-native.mjs` (25 checks, covering every risk-flag state, clean wearable, phone/accessory approval, retries, concurrent finalization, receipt consumption, forged roles/settings, media replacement, drift/pin/rollback) on fresh private PG17 clusters. Fixture limits: pgcrypto is a `sha256()` shim, Vault is a stub, and moderator/AAL2 identity is the fixture's `request.staff` stub (no real Auth/JWT). `azure-native.mjs` installs, in the hosted order, Accessories foundation + activation, the Azure finalizer, then Wearables foundation and activation, and verifies both Wearables postflights and the Azure postflight natively, the clean-listing auto-approval path, replaced-media downgrade, moderator-only approval of a flagged listing (seller, service role and forged settings refused), and client ACL/RLS isolation.

**Finding W-AZ-1 (open, not fixed here).** For a listing carrying a Wearables risk flag (`other_model`, `other_brand`, `still_paired`, `unknown_pairing`), an Azure `no_review_flags` outcome tries `UPDATE listings SET status='active'`; the Wearables guard correctly refuses it (no bypass), but the finalizer then **raises** instead of routing to admin review. The request stays `claimed`, the receipt unconsumed, and every retry raises until the lease expires. Resolving it needs a reviewed change outside the pinned SQL (for example, the finalizer routing flagged wearables to `routed_to_admin`); both pinned SQL files are unchanged in this patch.

## Rollback
